## Product Goal

Rupelian Player is a lightweight, professional Windows x64 desktop video player for language learning, intended for a worldwide audience. It combines dependable playback with interactive subtitles, vocabulary, translation, and contextual AI tutoring. It is built with Tauri instead of the earlier Python/PySide implementation. The English public repository describes the current development status; a globally distributed, signed stable release remains a separate future milestone.

**Brand naming:** The public product name and window/page title are `Rupelian Player`. Tauri's `mainBinaryName` explicitly keeps the binary name `rupelian`. The core brand, logo wordmark, package/crate name, executable (`rupelian.exe`), runtime (`rupelian_lib.dll`), application identifier (`com.webler.rupelian`), and new data/file names use `Rupelian` / `rupelian` without `Player`. Keep the existing visual design. The repository checkout path is not renamed during development.

On first use, `Documents\Lingo Cinema` is copied into a staged `Documents\Rupelian` directory when the new directory does not exist; encrypted credentials, YouTube playback access, translations, settings, and a consistent SQLite snapshot (including committed WAL data) are preserved without changing the old data. Existing Rupelian data wins. Isolated `RUPELIAN_DATA_DIR` (or legacy `LINGO_CINEMA_DATA_DIR`) overrides skip migration. Existing internal `__LINGO_*` test hooks, modal events, connector protocol markers, and the optional portable payload signature remain compatibility identifiers. Pre-rename packages and validation reports remain historical and are not regenerated by a source rename.

The application should:

- Play local videos with responsive native-looking controls.
- Stream YouTube videos with working play, pause, seek, volume, speed, quality selection, and captions.
- Provide interactive subtitles, translation, vocabulary saving, and AI-tutor features.
- Match the supplied visual reference as closely as possible. Do not casually redesign it.
- Run as a real desktop application rather than as a normal browser page.
- Eventually ship as a self-contained Windows package that does not require users to install Node.js, Rust, Visual Studio, Python, or WebView2 separately.

## Technology and Architecture

- Desktop shell: Tauri 2. On Windows a small Rust EXE paints a native loading window before dynamically loading `rupelian_lib.dll`, which owns Tauri, WebView2, and the player services. Keep both build outputs together for ordinary development. The folder-style portable keeps the DLL and resources adjacent to the EXE; the optional single-EXE package extracts and caches them separately.
- Frontend: Vite, vanilla JavaScript, HTML, Tailwind-generated CSS, and targeted custom CSS.
- Backend: Rust commands exposed through Tauri.
- Local persistence: user-owned durable data lives under the operating-system Documents directory in `Rupelian`. `settings.json` stores non-secret settings and playback progress, `credentials.json` stores per-provider API keys encrypted with Windows DPAPI for the current Windows account, `rupelian.sqlite3` stores the vocabulary/phrase library through bundled `rusqlite`, and `Translations` stores reusable AI subtitle progress as JSON plus SRT. The frontend keeps matching local-storage values only as a cache and one-time migration source; plaintext API keys and OAuth tokens are never written to settings, SQLite, local storage, or the WebView.
- Local playback: filesystem-backed videos use an embedded native libmpv engine behind a transparent Tauri WebView inside an opaque black Windows host, with hardware decoding and native seeking across containers/codecs such as 10-bit HEVC MKV. The desktop HWND must remain non-transparent; only the WebView backing is released after startup. Browser-originated `File` blobs retain the HTML-media path because they have no filesystem path; the cached H.264/AAC FFmpeg conversion remains only as an emergency fallback when native initialization fails. FFprobe discovers embedded subtitle streams and FFmpeg extracts text-based softsubs into the interactive cue system. Development can use FFmpeg tools from `PATH`, while distributable builds bundle the platform binaries and libmpv runtime.
- YouTube resolution: bundled `yt-dlp` plus bundled Deno for YouTube JavaScript challenges.
- YouTube playback: direct media URLs are hidden behind a local Rust HTTP proxy. The bundled libmpv instance plays video and optional external audio with a single audio-master clock and shared buffering. The synchronized HTML-media path remains a fallback when native initialization or the native load command is unavailable. The proxy stitches bounded upstream byte ranges into one seekable downstream resource, including resuming a truncated or timed-out response from the exact next byte.
- YouTube access: browser connection is for playback only. Like, subscriptions, playlist saving, official OAuth account actions, and the persistent browser action channel have been removed at the user's request. Settings prepares a temporary loopback URL to paste into the existing signed-in browser profile. A Manifest V3 connector reads only YouTube cookies after an explicit trusted Connect click and posts them directly to Rust for current-user DPAPI storage. It does not launch a managed browser, create a profile, or force Google sign-in. Public playback needs no session.
- Windows distribution: the current multi-file portable folder uses the installed system WebView2 and keeps the runtime DLL, media helpers, and native libraries beside the EXE, avoiding first-use payload extraction. The optional single-EXE build also uses the installed WebView2 but extracts its embedded payload once into Local App Data. The optional fixed-WebView2 configuration remains available only for explicitly requested builds.
- Desktop file opening: startup file arguments are consumed by the frontend, and the Tauri single-instance plugin forwards later file-open requests to the existing window. Bundle metadata declares the supported video file associations; portable users can also select the EXE through Windows `Open with` / default-app settings.

## Current Behavior

### Startup Experience

- The startup cover's red play mark, dark radial surface, and animated progress line are reused by the in-player waiting surface. The shared loader covers local opening and compatibility conversion plus YouTube startup, buffering, seeking, stream recovery, and quality changes; YouTube metadata discovery uses a compact version inside its modal instead of leaving the dialog visually idle.
- Windows first paints a lightweight native loading window from the small entry EXE, before loading the player DLL, WebView2, SQLite, or libmpv. It has no top bar; its entire surface supports native dragging. Clicking into another application minimizes this temporary loading window while initialization continues. Its independent message loop animates the progress line and accepts Alt+F4 or taskbar Close immediately while components load. Only after that first paint does the entry EXE prepare any portable payload and load the runtime DLL on the main thread. A normal second launch focuses the existing player without a new cover or frontend reload. Other platforms retain the direct Tauri entry path.
- Tauri creates one initially hidden main WebView with an opaque dark backing inside an opaque native HWND. Once its shell paints, Rust positions it over the native loading window, preserves moved/minimized state, releases only the WebView backing for libmpv, shows the player, and closes the native cover. The HWND stays opaque black even if mpv is absent or the page is transparent. If the loading window was minimized, the player stays minimized and retains the last visible loading-window position for restoration; it does not interrupt the other application. Click-away minimization applies only during this native loading screen. There is no second WebView or artificial reveal/fade delay. If the native cover cannot be created, Tauri shows the main window directly. Runtime-load failures display an error; a stalled frontend leaves the closable native surface visible. The empty player stage has a local gradient fallback while its poster decodes. It remains opaque until mpv reports a selected video track, configured video output, and real frame dimensions, then becomes transparent for the native picture. The hidden thumbnail placeholder is local and lazy-loaded.
- The interactive player shell is initialized from the synchronous WebView cache and revealed after two animation frames. Authoritative Documents settings and DPAPI credentials, the SQLite library, and native libmpv initialize independently after that first paint. Documents values hydrate the live controls without overwriting a setting the user changed during startup; startup file arguments wait for persistence hydration so resume state is available, while native initialization runs in parallel.
- `window.__LINGO_STARTUP__` and body readiness data attributes expose shell, native backing release, persistence, library, and native-engine milestones. `nativeStartup` separately records entry, native first paint, runtime-load start, runtime entry, and shell handoff, preserved across document reloads. The startup smoke test requires first paint before runtime loading, one live WebView, and persistence/library completion after the shell. Its first-paint limit is 500 ms from Rust entry and its shell limit is 2.5 seconds from navigation; these are regression limits, not universal launch guarantees. Process benchmarks measure the initial native surface separately from usable player controls. Disk, antivirus, WebView2, and first-use extraction can change timings.

### Local Playback

- Local files can be opened from the player and dropped onto it.
- On Windows the main WebView starts hidden behind the native loading window but deliberately keeps `focus: true` and native `dragDropEnabled: true` in Tauri configuration. Do not combine hidden creation with `focus: false`: current Wry/WebView2 then fails to register its native drop target and Explorer shows the forbidden cursor. The loading-window handoff already minimizes the player before its first show when the user has switched away, so this setting does not override that startup behavior.
- Opening a filesystem video automatically discovers adjacent `.srt`, `.vtt`, `.ass`, and `.ssa` sidecars whose filename is identical to the video stem, includes the full video filename, or adds a dot-separated language/variant suffix such as `movie.fa.srt`. The exact-name match is preferred, every match is added to the subtitle list, and the preferred match is activated automatically.
- Dropping one or more supported subtitle files while media is loaded adds them to the existing subtitle list and activates the newly dropped track. Native filesystem drops preserve the real paths; synthetic browser drops parse the file bytes directly.
- Launching the app with a supported video path opens that video immediately. If the app is already running, a second file-open launch focuses the existing window and sends the new path to it instead of leaving a blank second player.
- Loading a new video clears subtitles belonging to the previous video.
- Filesystem-backed local playback initializes libmpv after the player shell paints and loads the source directly without a whole-file compatibility transcode. Playback state, time, duration, volume, speed, pause, and exact seek are synchronized into the existing HTML controls. Local seeks never display the network-buffering overlay. mpv's `gpu` renderer with explicit Direct3D 11 output and `hwdec=auto-safe` is the primary Windows path; it preserves hardware decoding and avoids the reproduced `gpu-next`/libplacebo device loss on Vega hardware with the bundled runtime. Exclusive D3D fullscreen is disabled because the app owns its embedded window. If native output fails after a file has otherwise loaded (which can leave audio running with `vid=no`), the app keeps the WebView opaque, destroys that mpv instance, and retries with `gpu`/OpenGL/software decoding for the remainder of the process. If native playback is unavailable after that retry, the prior HTML-media and cached FFmpeg compatibility path remains available.
- Thumbnail decoding starts only after primary playback is established and is suspended during every main-video seek so the hidden preview decoder cannot delay startup or seeking.
- Filesystem-backed files opened from the picker or native operating-system drop use libmpv for common MP4, WebM, MOV, MKV, AVI, WMV, FLV, MPEG, transport-stream, VOB, Ogg video, 3GP, and ASF containers. Synthetic browser `File` drops keep the WebView path; unsupported files there cannot use native playback because no real path is exposed.
- Files opened by path or native operating-system drop are scanned asynchronously for embedded subtitle streams only after the first native frame is presented, so subtitle work cannot delay playback startup. Text softsubs such as ASS/SSA, SubRip, WebVTT, and MOV text are listed in a dedicated `Embedded subtitles` group; the default text track (or first usable text track) is extracted and activated automatically while every detected track remains independently selectable. Extracted text is cached by path, size, modification time, and stream index, and FFprobe/FFmpeg run below normal priority on Windows. Image-based PGS, DVD/VobSub, DVB, and XSUB streams are identified as `Image only` because selectable language-learning text requires a future OCR pipeline.
- Timeline clicking and dragging work, including preserving the pointer offset when grabbing the thumb.
- Timeline thumbnails use a 60-frame cache. Native local playback requests low-quality 320px FFmpeg frames through a persistent disk cache, starts background prewarming only after the first frame, and defers it again during user seeks. WebView-compatible blob playback keeps the hidden HTML decoder. YouTube preview extraction uses a dedicated low-resolution stream, activates only on timeline hover, and never background-prewarms. After capturing the requested frame, leaving the timeline, or seeking the main player, its hidden decoder is detached to stop background downloads; cached frames do not reopen the connection. Cached imagery remains visible while missing frames are generated without re-entering a loading state.
- Timeline thumbnail cards contain only the preview image and timestamp; do not restore a filename/chapter row or pointer below the image.
- Timeline thumbnail cards track the pointer immediately with no positional CSS transition; image decoding and cache replacement remain asynchronous and must never make the card itself trail fast pointer movement.
- Volume supports click and drag, the Up/Down arrow keys, and vertical mouse-wheel movement over the player in 5% steps. A compact, short-lived OSD confirms volume changes and timeline seeks without covering the center of the video.
- Filesystem-backed local videos expose multiple embedded audio streams reported by libmpv in an Audio flyout. The preferred language is selected automatically (including common ISO 639-2 three-letter metadata such as `eng` and `jpn`), and users can switch tracks without reloading the video. Browser-blob fallback exposes multiple tracks when WebView2 provides the HTML audio-track API.
- Local and YouTube playback positions are stored per stable media identity. Reopening unfinished media offers Continue or Start over before replacing the current source; near-end and completed positions are discarded.
- Play and pause use the same fixed-size circular control. SVGs and their paths inside every button are explicitly non-draggable and pointer-transparent, so clicking directly on an icon always reaches its parent control instead of being swallowed by the Tauri drag region.
- At normal desktop widths, the five-button transport cluster is centered on the player independently of the left and right control wings; below 1024 px it returns to the compact flexible layout to avoid collisions.
- The header and empty viewport can drag the desktop window. During YouTube playback, a dedicated transparent video-surface drag layer also lets users move the native window from the picture itself without covering subtitles or controls; double-click fullscreen remains available.
- Double-clicking loaded video toggles native window fullscreen in both directions.
- Maximizing and fullscreen transitions retain a healthy native picture instead of blanking it for fixed delays; the opaque native host protects the desktop throughout resizing and output recovery. Fullscreen placement and maximized-state restoration run together on the Windows UI thread without first showing the normal-size window. Controls remain visible through transient focus/mouseleave events and get a fresh auto-hide interval afterward. Rapid fullscreen clicks are serialized instead of discarded during a transition. Near EOF, mpv captures the actual full-resolution decoded frame into the app cache. At EOF the WebView becomes opaque and displays that retained final frame; replay keeps the still visible until live native output is revalidated. EOF also fills the timeline and moves its thumb to 100%, even when the last decoded frame's timestamp is shorter than the container duration; the actual playback timestamp remains available separately.
- Header and bottom controls hide after two seconds when the pointer is outside them. UI shading is confined to a soft 160 px multi-stop top gradient and 168 px bottom gradient, leaving the middle of the video unfiltered; both gradients fade out with the chrome.
- The initial desktop window is centered at 1180×720 with a 900×600 minimum.

### Header State

- The top bar does not display the current media title or format. The right-side quality control remains hidden before media is loaded and appears only after valid media metadata is available.
- The left `YouTube Stream` pill is an action that always opens the YouTube dialog; it does not change to a misleading `Local File` status when local media is playing. Subtitle Studio is not duplicated in the header and remains accessible from the bottom CC workflow.

### YouTube Playback

- The YouTube dialog starts empty and stays deliberately compact: URL input, resolved video preview/status, and Play/Cancel, with an Open YouTube Settings recovery button for session errors. Browser-session controls and per-open quality/caption selectors are not shown inside this dialog; static sample data must not be reintroduced.
- `Find video` resolves real metadata, thumbnail, seekable formats, and caption tracks while showing the shared branded waiting state and an accessible busy status. Starting the resolved video closes the modal first so the full in-player loader remains visible throughout initial playback preparation.
- Starting playback applies the persisted YouTube defaults for adaptive/fixed quality, initial volume, preferred audio language, and preferred caption language. Specific caption languages load automatically when available; `Auto` prefers English and creator captions before other detected tracks, while `Off` starts without captions. Users can still change quality, audio, and captions from the in-player controls for the active video.
- Playback supports both muxed media and separate video/audio streams. When YouTube exposes a compatible muxed rendition at a requested resolution, it is preferred to avoid a second download and decoder; separate audio is activated only for video-only renditions or when the user explicitly chooses an alternate audio track.
- The local proxy serves GET, HEAD, and OPTIONS and preserves byte-range semantics. GET transfers use upstream requests no larger than 4 MiB, below YouTube's large-request throttling threshold; chunks stream immediately and downstream backpressure bounds downloading. Connect and read deadlines are 8 and 10 seconds. Transient server failures and interrupted response bodies are retried up to three times, resuming from the exact next byte without duplicating data. Invalid or changed ranges are rejected; dropping a consumer cancels its upstream transfer. Signed URLs remain behind loopback proxy tokens.
- Native YouTube playback uses libmpv's audio clock for both streams, an initial/rebuffer reserve of about two seconds, and up to 60 seconds of read-ahead (128 MiB forward / 32 MiB backward limits per demuxer). It does not activate the main HTML video/audio elements. Network options are scoped to each load and are restored when returning to local media.
- Quality and audio-language changes preserve playback time, volume, speed, and playing/paused state. Play/Pause clicks made while a replacement source is opening are reapplied after `file-loaded`. Opening the same resolved video again invalidates any queued native load, waits for the previous mpv stop to finish, and explicitly resets audio selection to automatic so stale replacement commands or track state cannot leave the replay silent. Native audio presence is checked so an external-audio failure is recovered rather than presented as healthy silent playback. A no-progress watchdog reconnects after 25 seconds, with bounded attempts and an explicit Play-to-retry state.
- Quality selection includes a YouTube-style Auto mode that chooses a stream from viewport and connection information, caps its initial desktop target at 720p for dependable startup, and reevaluates it when those conditions change. Two genuine rebuffer events within one minute step Auto down to the next available resolution; the resulting ceiling remains for that media so window resizes do not immediately undo the downgrade. Manual quality choices are never silently changed.
- YouTube discovery excludes AV1, HEVC, and mismatched codec/container combinations that are not reliably decodable by the bundled WebView2 runtime. Playback formats are limited to H.264 in MP4 or VP9 in WebM with compatible audio; an HTML-fallback runtime decode failure automatically retries another format, preferring H.264 at the same or lower resolution.
- Creator and auto-generated YouTube captions are returned together and displayed as visually separated groups in one selector. JSON3 auto-captions merge duplicate events and clamp cue overlap before entering the interactive cue system.
- Alternate YouTube audio tracks are resolved as independent compatible streams, grouped by language/track label, and exposed through the same Audio flyout used for local media. The preferred language is applied on load, manual changes preserve playback position and synchronization, and the selected language survives quality changes and refreshed signed URLs.
- Timeline seeking is committed once on pointer release. Native YouTube seeking, stalls, quality changes, and rebuffering are coordinated by libmpv and reflected in the shared in-player loader; local seeks remain loader-free. In the HTML fallback, every internal interruption—seek, quality switch, buffering, stream refresh, or recovery—pauses companion audio before stopping or replacing video, so sound never continues over a frozen picture. YouTube startup, post-seek playback, and stall recovery pass through a shared video/audio buffer gate: normal startup waits for roughly three seconds of both streams and rebuffer recovery targets roughly 4.5 seconds, with a guarded lower threshold only after an extended slow connection. Neither stream resumes alone. Replaced buffer gates invalidate pending resume promises and release their in-flight lock so overlapping seek/waiting events cannot strand fully buffered playback. Separate YouTube audio seeks to the destination as soon as video seeking begins so both streams buffer in parallel; hard audio seeks are deduplicated and reserved for real clock jumps, while small steady-state drift is corrected with a bounded playback-rate adjustment so words are not repeated.
- YouTube metadata includes a dedicated preview proxy chosen near 240p before playback formats are truncated, preventing thumbnail extraction from competing with playback at an unnecessarily high resolution.
- Transient YouTube media errors preserve the active video, subtitles, and last good playback time. The player first reloads the current proxy and, after a repeated failure, resolves fresh signed streams; automatic recovery resumes playback, while a later Play click retries the same YouTube source instead of opening the local-file picker. Codec fallback prefers the closest compatible format at or below the selected resolution and only steps to the nearest higher resolution when no lower candidate remains, avoiding an unnecessary bandwidth jump after a low-resolution failure.
- Settings > YouTube always offers **Connect browser**, even before media is loaded. It prepares a 30-minute loopback URL without launching anything. Pasting it into the already signed-in browser profile stays in that tab; the installed connector shows **Connect my current YouTube account**. Only after the trusted user click does the extension send YouTube access directly to Rust. Completion updates Settings automatically, including while Settings is closed. Cancel and expiry invalidate the attempt without closing personal browser windows, and late/used links cannot overwrite saved access. The in-app **Open** button opens the URL normally in the default browser, with no profile or debugging flags; copying the URL is the reliable way to choose a particular already-open profile.
- Windows Chromium App-Bound Encryption and active cookie database locks still make direct desktop extraction unreliable; no default-profile remote debugging, database copying, or decryption bypass is used. The browser connector uses the browser's own cookies API with YouTube-only host permissions. Only YouTube-domain cookies with an unexpired sign-in cookie are accepted into DPAPI-encrypted Documents\Rupelian\youtube-session.json; secret values never enter the player WebView, connection-page DOM, settings, or browser local storage. Manual Netscape cookies.txt import remains under Connection options. Access can expire/revoke and require reconnecting.
- The connector source lives in `src-tauri/browser-extension/` (manifest, service worker, trusted-click content script, English setup instructions). Rust embeds these files and exports them into the stable per-app Local App Data `youtube-browser-connector` folder when preparing a link or opening setup. Development installation uses chrome://extensions / edge://extensions > Developer mode > Load unpacked once in the actual signed-in profile. Reload an already-open connection tab after installation. This is not a silently installed extension; store publishing remains pending. A browser-supplied UA is never treated as access to the user's account.
- YouTube Settings uses one compact browser-access card: status, Connect/Refresh, Disconnect, and a pending link row only when connecting. Setup and manual cookies.txt import are collapsed under Connection options. Failed-video checking/retry appears only when opened from a playback access error. Playback defaults follow the card. Existing saved playback access is preserved; obsolete OAuth/bridge credential files are ignored rather than deleted.

- Browser connector v3 is playback-only: cookies permission, no background action socket, scripting, storage, alarms, or YouTube watch-page content scripts. Updating the exported connector removes the two obsolete action script files. Already-installed v2 extensions should be reloaded once from the browser extension manager.

### Subtitle Workspace and AI Translation

- Subtitle controls are context-aware rather than speculative. Before a playable local or YouTube source is known, the CC trigger and all source-specific subtitle actions remain hidden. A known local source exposes only local subtitle loading; a known YouTube source exposes caption fetching only when real caption tracks were detected. Master, multi-track, sync, size, and AI translation controls appear only after a subtitle track with cues is loaded.
- The bottom CC control opens one unified flyout for local subtitles, YouTube creator captions, and YouTube auto-generated captions. These sources remain in one selector but are separated by visible group headings; the AI modal does not duplicate subtitle-source selection.
- Multiple local subtitle files can be loaded together. SRT, WebVTT, ASS, and SSA are parsed directly; common FFmpeg-readable text formats (`.sub`, `.sbv`, `.smi`/`.sami`, `.lrc`, `.mpl2`, `.mpsub`, `.pjs`, `.rt`, `.stl`, `.aqt`, and `.jss`) are converted through the bundled FFmpeg path. Local parsing accepts UTF-8 (with or without BOM) and UTF-16 little- or big-endian text. ASS alignment/position overrides (including `\\an8`), primary colors/alpha, bold, italic, underline, strikeout, font and size changes; SRT HTML-like formatting; and WebVTT cue positioning/class colors are normalized into a safe structured rich-text cue model. Plain text remains available for selection, translation, vocabulary, and tutor workflows. Bitmap PGS/VobSub subtitles still require OCR.
- Embedded text subtitle tracks from local containers enter the same primary/secondary, synchronization, translation, vocabulary, and AI-tutor workflow as external subtitle files.
- A master switch enables captions, and Multi-Subtitle Mode assigns a primary and secondary track for simultaneous display. Track cards show their real source, language, load state, and cue count.
- The flyout provides 50 ms synchronization steps and cyclic subtitle sizing from 80% through 150%. Subtitle overlays show the independently selected primary and optional secondary tracks without displaying timestamps. Text uses antialiased, legibility-optimized rendering; outline presets use a thin WebKit stroke plus soft shadow rather than multiple offset shadows. Settings provide persisted Cinema, Classic, Minimal, high-contrast yellow-on-black, and Golden yellow-without-background presets, arbitrary installed font-family selection, and bottom-distance controls. Opening the font picker enumerates local families through Chromium's Local Font Access API after the user click and presents them in a searchable, scrollable menu with each family previewed in its own typeface. Manual font-family entry remains available as a fallback when enumeration is unavailable or permission is denied.
- The AI translation studio supports target-language selection, current-line translation, full-subtitle batch translation, and live translation with a rolling 60-cue look-ahead window. Full translation sends up to 16 chronological target cues per request and live translation drains that window in batches of up to 12; every request also supplies up to five read-only preceding cues, five following cues, cue timing, the video title/file name, source type, subtitle-track label, and source language. The provider is instructed to act as a context-aware subtitle translation agent: it must preserve continuations across cue boundaries, avoid forcing fragments into standalone sentences, translate only target IDs, and return one ordered result for every requested cue. The backend rejects missing, reordered, extra, or empty results. Normal look-ahead batches remain serialized, but seeking clears obsolete queued work, rebases the live window at the destination, and dispatches that destination immediately even if an older request is still completing. Live pending cues display a neutral `Translating…` placeholder instead of exposing the original-language line; each placeholder is replaced in place when its translation arrives. The live control and studio status explicitly distinguish active translation from a user-canceled state, with Cancel and Resume actions; canceling restores the source subtitle as primary while retaining completed translated cues as a selectable track. Progress, request count, and token usage are based on real responses rather than sample data.
- AI translation results become real subtitle tracks in a dedicated group above every local and YouTube source. Starting current-line, full-subtitle, or live translation automatically makes the translated track primary; when Multi-Subtitle Mode is active, its source remains secondary. Full translation tracks use source-text fallbacks while work is pending, while live translation uses the neutral pending placeholder. Each translated language remains independently selectable, and translations are never injected implicitly beneath their source track.
- Every successful AI translation batch is durably checkpointed under `Documents\Rupelian\Translations` as a metadata-rich JSON project and a reusable UTF-8 SRT. Partial projects retain translated cue indexes, request/token counts, provider/model information, and total progress; reopening the same media and matching source subtitle restores those translations and activates the saved translated track automatically. Completed projects restore in the same way without another provider call.
- While translation is running, the studio reports `Translating subtitles with <model>…` (or the live look-ahead equivalent) in the current English interface, and both its status and progress identify the actual configured model.
- Translation providers include OpenRouter, OpenAI, Google Gemini, Anthropic Claude, Groq, Mistral, DeepSeek, Together AI, xAI, Cerebras, Fireworks AI, Perplexity, local Ollama, and a custom OpenAI-compatible endpoint. Known providers use fixed built-in endpoints, so only the custom provider exposes endpoint configuration.
- OpenRouter loads its current public model catalog without requiring a key. Other catalog-capable providers load the models available to the supplied account, and Ollama lists locally installed models. The shared searchable selector shows model IDs, context sizes when reported, and normalized input/output prices when the provider exposes them; OpenRouter and xAI pricing are converted to cost per million tokens for display. Providers without a dependable catalog and catalog failures retain manual model-ID entry.
- AI provider configuration lives in the dedicated Settings modal rather than inside the translation workflow. Non-secret AI settings are stored in the Documents settings file per provider. On Windows, every provider API key is encrypted separately with current-user DPAPI and stored in `Documents\Rupelian\credentials.json`, then restored when the app reopens; clearing a key removes its encrypted value. Plaintext keys are sent to the configured provider through the Rust backend but are never written to settings, SQLite, or local storage. Non-Windows builds currently keep credentials session-only until a native keychain backend is added.

### Interactive Vocabulary and AI Tutor

The initial Python-style analysis becomes the first exchange in the agent history. ## UI Rules

- Preserve the layout, proportions, dark surfaces, YouTube-red accents, spacing, and control placement from the reference design.
- The top video shade uses a long multi-stop fade with no visible cutoff, remains confined to the upper chrome region, and hides with the chrome; do not replace it with a short or hard-ended gradient.
- Both the header/dock backgrounds and the extended video shades use pure black RGB gradient stops; keep their existing alpha fades rather than introducing a gray tint.
- Functional state must replace fake/static content. Never display a capability, quality, caption, account state, or video detail that has not actually been detected.
- Controls that are not meaningful before media loads should be hidden or disabled.
- Avoid browser-like artifacts; this must feel like a polished desktop player.
- Keyboard operation remains functional through the editable centralized shortcut map, but shortcuts are blocked while a modal or text-entry control has focus. Buttons suppress the WebView's default white focus outline so Space/Tab interaction does not add a browser-style border to the player UI.
- Keep window minimize, maximize/restore, close, fullscreen, and drag behavior operational after UI changes. The custom Close button must invoke Tauri's normal window close directly; persistence must never cancel or recursively reissue a close request.
- Subtitle overlays display subtitle text only; do not show cue start/end timestamps in the overlay.
- Flyouts remain open for every interaction that originated inside them, including controls that rerender and replace the clicked DOM node; a genuine outside click closes the flyout. Overlay-backed dialogs close when their dimmed backdrop is clicked but remain open for clicks anywhere inside the dialog surface.
- Opening any overlay-backed modal pauses active local or YouTube playback, cancels an active YouTube buffer gate, and blocks playback shortcuts behind the dialog. Closing a modal never resumes playback automatically; the user must explicitly press Play.

Packaging is opt-in, only on an explicit user request. The current Windows x64 multi-file package uses `src-tauri/tauri.portable-no-webview.conf.json` and `scripts/package-portable-folder.ps1`. It keeps the player runtime DLL, libmpv, yt-dlp, Deno, FFmpeg/FFprobe, application-local VCRUNTIME140, and Vulkan loader DLL beside the small entry EXE; it excludes WebView2 and all installers. Nothing is unpacked on first launch. Durable data remains in `Documents\Rupelian`. Windows 10/11 x64 with WebView2 already installed is the intended target.

Build on the native x64 host with `RUSTFLAGS=-C target-feature=+crt-static` and `npm.cmd run tauri build -- --no-bundle --features custom-protocol --config src-tauri/tauri.portable-no-webview.conf.json`, then run `powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/package-portable-folder.ps1`. Let the Windows Cargo runner keep the large Cargo target under the current account's Local App Data; do not override it back into `src-tauri/target`, which can add more than 12 GiB to the project directory. The Windows Cargo runner builds both the entry EXE and runtime DLL; a direct Cargo build must likewise include both targets. The Cargo `custom-protocol` feature must be enabled so the release serves its embedded frontend instead of the development URL. Runtime DLLs are in `packaging/runtime`; source/license references are in `packaging/THIRD-PARTY-NOTICES.txt`. The release hides its console and resolves helpers relative to the loaded runtime DLL, never from the developer source tree or PATH.

The optional Windows x64 single-EXE package uses the same no-WebView build plus `scripts/package-portable.ps1`. Its entry EXE paints the native loading surface before reading the appended payload. On first use it verifies the embedded extractor/archive SHA256 and extracts into `%LOCALAPPDATA%\Rupelian\portable-runtime\<payload-hash>`. A mutex serializes extraction, a completion marker permits subsequent launches to reuse the files without decompression, and a Windows job cancels extraction when the loading window is closed. The cache remains after exit and is recreated if required files disappear.
